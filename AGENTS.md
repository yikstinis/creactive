# Agent instructions

Creactive is a cross-platform component library built on React Native.

This file holds the working conventions for any AI agent contributing code here. Keep it current as conventions are established — update it whenever a new rule is agreed on.

## Naming

- **Constants** — `UPPER_SNAKE_CASE` (e.g. `DEFAULT_VALUES`).
- **Test files** — colocated with the code under test, suffixed by runner: `*.jest.test.{ts,tsx}` (unit), `*.playwright.test.ts` (web visual regression), `*.detox.test.ts` (native visual regression).

## Comments

Default to no comments — add one only for a non-obvious constraint, invariant, or reasoning. Format multi-sentence comments as multi-line `//` comments (one sentence per line), not a single long line.

## Workflow

- Run `npm run tsc` (TypeScript typecheck), `npm run eslint`, and `npm run jest` (unit tests, across the `native` and `web` projects) before committing.

## Testing

All functionality must be covered by tests — every code path that's written, including edge cases, not just the happy path.

Nest `describe` blocks to mirror what's under test:

1. Outer `describe` — the `@/...` path alias of the file under test (e.g. `@/helpers/dimension/dimension`).
2. Next `describe` — the name of the export from that file being tested (e.g. `Dimension`).
3. If that export is an object, a further `describe` per property being tested.

When the set of possible inputs is exhaustively enumerable (e.g. an enum), test every member rather than a sample.

### Visual regression testing

The root `App.tsx` is an Expo app entry point that stays generic forever: it only owns the `SafeAreaProvider`/`useSafeAreaInsets()` padding wrapper and `<StatusBar hidden />`, then renders `VisualTestHost` (`src/testing/host.tsx`). It goes through the normal `tsc`/`eslint` checks like the rest of the repo.

- Each component's visual-test screen ("scene") is colocated as `<component>.<prop>.scene.tsx`, exporting a `VisualScene` (`{ id, Scene }`, typed in `src/testing/scenes.types.d.ts`). Register a new scene with one line in `src/testing/scenes.ts`'s `VISUAL_SCENES` array — `App.tsx`/`VisualTestHost` never need touching again.
- The scene's enumerable case list (e.g. `VIEW_PADDING_CASES`) and its scene id constant live in a separate colocated `<component>.<prop>.cases.ts`, imported by both the `.scene.tsx` file and the Playwright/Detox tests. Keep this file free of `react-native`/JSX imports: Playwright's test runner is plain Node and can't transform `react-native`'s own source, so a test importing anything that transitively pulls in `react-native` (like the scene component itself) fails with an opaque parse error (e.g. `Unexpected token 'typeof'` from deep inside `react-native`, misreported against the importing file). The `.scene.tsx` file itself should only ever be imported by `src/testing/scenes.ts`, never by a test file.
- `VisualTestHost` renders a nav row of every registered scene (`scene-nav-<id>` testID'd `Pressable`s) plus the currently selected scene's own render. A Playwright/Detox test for a given scene taps its `scene-nav-<id>` once up front (before driving that scene's own cases), the same tap-to-select mechanism used for cases below.
- Both runners drive their scene through the same three-step `VisualDriver` interface (`src/testing/visual.types.d.ts`): `initialize(sceneId)` selects the scene, `enable(navTestId, targetTestId)` taps a case's nav entry and waits for it, `match(targetTestId, group, name)` screenshots and compares against the baseline. Each platform implements it once, at the project root, and every test calls the three by name with no prefix — `detox.setup.ts` (wired into Detox's Jest run via `setupFilesAfterEnv`) exposes them as ambient globals, `playwright.setup.ts` exposes them as same-named fixtures on an extended `test` (imported via the `@root/*` tsconfig path alias instead of `@/*`, since it lives outside `src`, and used instead of `@playwright/test`'s own `test`) — so a component's `.detox.test.ts`/`.playwright.test.ts` pair only loops its cases calling `initialize`/`enable`/`match`, with no platform-specific screenshot/crop/navigation code of its own.
- **Web**: Playwright (`*.playwright.test.ts`, colocated with each component) runs against `expo export -p web`'s static build.
- **Native**: Detox (`*.detox.test.ts`, colocated with each component) compares screenshots via `jest-image-snapshot`.
- Baselines are committed PNGs, kept in a `snapshots/` folder next to each component's visual test files, one subfolder per prop under test (e.g. `snapshots/padding/`). Regenerate them on CI, not locally — cross-machine font/anti-aliasing differences cause false-positive diffs otherwise.
- Visual suites are opt-in and stay out of `npm run tsc`/`eslint`/`jest` — they're slow and environment-dependent (browser/simulator/emulator boot).
- When a component's visual test must cover every value of an enumerable prop (e.g. View's padding scale), list the cases once in that component's `<component>.<prop>.cases.ts` and derive the scene, the Playwright test, and the Detox test from it — covering a new case is then a single line there. The scene renders one case at a time (`<component>-<prop>-<case>` testID) plus a nav row of per-case testID'd `Pressable`s (`<component>-<prop>-nav-<case>`); each test taps a case's nav entry, then screenshots its testID. File the resulting snapshot as `snapshots/<prop>/<case>.{platform}-{device}.png` (e.g. `snapshots/padding/x6l.ios-iphone-17.png`), suffixed to match the `snapshot-test-{platform}-{device}` job naming in maintain.yml — this groups a case's baselines across every platform side by side, for reviewing one case's cross-platform rendering as a unit.
- Each case's screenshotted element is a fixed-padding (80px) container in one color, wrapping the prop-under-test's own box in a contrasting color, itself wrapping 3 fixed 32×32 reference squares (colors distinct from both, so all 3 stay visible) — the squares give a constant-size reference and the contrasting fill makes the prop's own box (e.g. its padding) a visibly distinct band, not just blank space indistinguishable from the fixed frame around it.
- Prefer tap-to-select navigation between cases (a `Pressable` per case, tapped by testID) over scrolling a shared `ScrollView` into position. A `ScrollView` + Detox's `waitFor(...).toBeVisible().whileElement(by.id(scrollViewTestID)).scroll(...)` looked simpler at first, but consistently hung the Android Detox run at the first case needing an actual scroll (Espresso's "waited for window focus... not request layout" - the app never recovered for the rest of that run afterward). Neither removing `react-native-safe-area-context` nor `disable-animations: true` on the emulator runner fixed it; switching to tap navigation (no gesture, one screen/case swapped in place) sidesteps the whole class of issue and is exactly as valid a "single app screen/launch" per AGENTS.md's testing rules.
- The container holding the currently-selected case needs its own `alignSelf: 'flex-start'` - View's default `alignItems: 'stretch'` on the parent otherwise stretches it to the full screen width regardless of viewport size (confirmed at both a 500px and a 1600px web viewport), which both hides the padding-driven size differences between cases and produces a screenshot dominated by empty background. Setting it on the container itself, not just `alignItems` on the parent, keeps "this view never stretches" a property of the screenshotted element rather than something that silently depends on an ancestor's style staying put.
- `App.tsx` wraps in `SafeAreaProvider` and applies `useSafeAreaInsets()` as padding on the root view - without it, a case positioned close enough to the top of the screen gets a device's notch/Dynamic Island rendered right into its otherwise-empty background band in the native screenshot (confirmed on the iPhone 17 simulator). This was tried and reverted once already for an unrelated reason (suspected, then ruled out, as the cause of the Android scroll hang below) - it's safe to keep now that navigation is tap-based instead of scroll-based.
- This crop/scale logic lives in the root `detox.setup.ts`'s `match()`, not in individual component tests. Detox's `element(by.id(...)).takeScreenshot()` (rather than `device.takeScreenshot()`) came back blank/all-background on this project's CI Android *and* iOS emulators for every case, sized correctly but with no content painted - a known class of issue on GitHub Actions runners, since element screenshots are drawn via the view's own `draw()` rather than reading back the actual compositor output. Use `device.takeScreenshot()` for native visual tests instead, then crop the case's own bounds out of it in JS to match Playwright's tight per-element crop: take the full-screen shot, read the case's `element(by.id(caseTestID)).getAttributes().frame` (screen coordinates), and derive the point-to-pixel scale from a full-screen-spanning root testID's own frame (`screenshot.width / rootFrame.width`) rather than assuming a platform-specific unit - `device.takeScreenshot()` returns raw pixels, but `frame` comes back in points on iOS and (empirically) already in pixels on Android, so this ratio comes out to the real device scale (e.g. 3 on an iPhone simulator) either way. Crop with `pngjs` (`PNG.sync.read`/`.write`, manual scanline copy), not `jimp` - jimp v1's format auto-detection calls a dynamic `import()` internally, which throws "invoked without --experimental-vm-modules" under Jest's default (non-ESM) setup; pngjs is plain synchronous CJS with no such issue, and we already know every input is a PNG so format detection buys nothing anyway.
- The crop comes out at the device's native pixel density (3x on the iPhone 17 simulator, ~1x on the Android Pixel 7 emulator per the point-vs-pixel note above), so `match()` downsamples it back to point-resolution with a hand-rolled `factor`x`factor` box-average (`downsamplePng` in `detox.setup.ts`, `factor = Math.round(scale)`) before comparing - otherwise a retina device's baseline would be `scale`x larger than Android's and Playwright's for the same logical size, defeating the side-by-side cross-platform comparison the `snapshots/<prop>/<case>.{platform}-{device}.png` layout is for. Verified once against the committed Android baseline: downsampling a 3x iPhone crop reproduced its Android counterpart byte-for-byte for these flat-color cases.
